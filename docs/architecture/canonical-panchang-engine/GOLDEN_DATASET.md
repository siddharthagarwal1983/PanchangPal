---

## 0. What is not true yet

This dataset **has no values in it.** 46 rows of keys exist; every expected-value column is
empty. Nothing can be validated against it today, and no release gate should read it until
§4's exit criteria are met.

It is written down in this state deliberately. ADR-033 Residual R1 records that the absence of
a golden dataset blocks the engine from ever being *registered*, and a blocker that lives only
in an ADR paragraph is harder to act on than one with a file behind it.

---

## 1. The rule that makes this dataset worth having

**Expected values come from independent references and NEVER from our engine.**

A dataset generated by the code it validates proves only that the code is self-consistent. It
would go green on the day the engine is wrong, and it would keep going green afterwards. TDD §6
therefore requires cross-checking against **Drik Panchang and mPanchang** — two independent
authorities — and reviewer approval on top.

Concretely, three things are forbidden:

1. Populating any expected column by running `PanchangEngine.compute()`.
2. Populating any expected column from a library we are considering adopting (that is the same
   error one layer out: it validates our choice of dependency against itself).
3. Recording a value without its `source` and `source_url`. **A golden value without provenance
   is an assertion, not a reference.** If a disagreement surfaces in a year, the only way to
   adjudicate is to re-read where the number came from.

## 2. Scope — `generic` only

ADR-033 B-3 ratified **`generic` alone** for v1. `north_indian`, `south_indian_tamil` and
`bengali` are deferred to the pandit reviewer and must not appear in this dataset; rows for them
would imply conventions nobody has ruled on.

✅ **`generic`'s four profile fields are RULED (ADR-033 B-5, 2026-08-09):** `month_scheme`
**purnimanta** · `tithi_reference` **tithi-at-sunrise** · `sunrise_convention` **upper limb +
standard refraction** · `day_division` **sunrise→sunset in 8 equal parts**. This matters for
collection: **a disagreement with Drik can now be adjudicated** as either a bug or a convention
difference, rather than being resolved in whichever direction makes the test pass.

⚠️ **Two caveats affect what may be filled.** The **Rahu Kaal weekday→segment mapping is
PROVISIONAL** until the reviewer confirms it, so `rahu_kaal_start`/`rahu_kaal_end` are collectable
from a reference but must not be compared against engine output until it is confirmed. And
`generic` is **purnimanta**, a North Indian convention — so **when reading a reference, set its
month scheme to purnimanta explicitly** rather than accepting the site's default, or the month names
recorded here will silently belong to a different scheme.

## 3. Sampling plan — why 46 rows and not 365

A uniform year of dates is a weak test: most days are unambiguous, and a dataset of ordinary
days would agree with any roughly-correct engine. The rows that discriminate are the ones where
conventions and time handling are under stress. Every stratum below is selected from facts
computable **without any astronomy** — calendar structure, the IANA database, and latitude — so
choosing them invents nothing.

| Stratum | Rows | What it stresses |
|---|---:|---|
| **S1-dst** | 18 | DST transition day ±1 at New York, Sydney, Auckland — both directions. Where `localDateIn` and sunrise interact worst. Issue #30 was a UTC-vs-local date bug that recorded the AU/NZ morning ritual against yesterday; this stratum is its regression surface. |
| **S2-solar** | 12 | March/September equinox, June/December solstice at New York, Sydney, **Anchorage**. Extreme sunrise spread; Anchorage (61.2°N) is where a sunrise convention and `day_division` over a very long or very short day get strange. |
| **S3-month** | 12 | 1st of each month at Auckland — even coverage across the lunar year so no month scheme is untested. |
| **S4-nodst** | 4 | Perth and Honolulu (no DST) at both solstices — **controls**. If an S1 row fails and its S4 counterpart passes, the fault is DST handling rather than the astronomy. |

DST dates are exact, read from the IANA database for 2027:
`America/New_York` 03-14 / 11-07 · `Australia/Sydney` 04-04 / 10-03 ·
`Pacific/Auckland` 04-04 / 09-26. Perth, Brisbane and Honolulu have none.

⚠️ **2027 tz data can change.** A country abolishing DST would move an S1 key and silently
change what the row tests. Re-derive the transition dates when re-baselining, and treat a moved
date as a dataset change requiring re-approval.

### What Phase 1 deliberately does not cover

**Near-boundary cases — the hardest ones — are absent, and cannot be chosen yet.** The rows that
most sharply separate a correct engine from a nearly-correct one are those where a tithi boundary
falls within minutes of sunrise, because that is where `tithi_reference` decides which day a fast
lands on. **Selecting such a date requires knowing where the boundaries are, which requires an
engine — the circularity is real.** Phase 2 resolves it: once a candidate engine exists, have it
*propose* near-boundary dates, then send those dates to the reviewer for independent cross-check.
The engine is allowed to choose the questions; it is never allowed to supply the answers.

## 4. Exit criteria — when this dataset becomes a gate

All four must hold before any CI job reads this file:

1. Every expected column in every row is filled, with `source` and `source_url` per row.
2. Each row is cross-checked against **both** Drik and mPanchang, and disagreements between the
   two references are recorded rather than silently resolved — a disagreement between authorities
   is information about tolerance, which ADR-033 B-4 deliberately left unset.
3. `checked_by` / `checked_on` are populated — reviewer approval is per-row, not per-file.
4. ✅ `generic`'s four profile fields are ruled (§2) — **met 2026-08-09**. ⚠️ The Rahu Kaal
   weekday mapping remains provisional, so those two columns cannot gate until confirmed.

Until then the gate is **not added**. `ci.yml`'s standing rule from B1 is that *a gate is added
when it can fail*, and two gates were de-declared for failing it. A festival-date gate today would
run against the seed's single `sample-festival` — significance *"Placeholder significance
(reviewer content to follow)"* — or against nothing at all, and pass either way.

⛔ **ADR-033 B-4's ratified criterion is "festival dates exact (0-day)", and there are no real
festivals to check.** Real reviewed festival content is §10.1 item 2. The engine and the festival
corpus are therefore blocked on the same reviewer, and that is worth knowing before either is
scheduled as if it were independent work.

## 5. Versioning

Keyed with `engine_version` per TDD §7. A change to the ephemeris, ayanamsa, a tradition profile
or the methodology bumps `engine_version`, re-runs this dataset, and invalidates `panchang_cache`.
Corrections never silently change a user's historical dates — they ship as a new version.

Filling values is itself a dataset version. Add rows in a new file rather than editing an
approved one, so an approval always refers to a fixed set of numbers.

## 6. Column reference

**Keys (generated — do not edit):** `row_id`, `tradition`, `location`, `tz`, `lat`, `lng`,
`local_date`, `stratum`, `rationale`

**Expected values (reviewer fills):** `sunrise`, `sunset`, `tithi`, `tithi_end_utc`, `nakshatra`,
`nakshatra_end_utc`, `yoga`, `karana`, `rahu_kaal_start`, `rahu_kaal_end`

**Provenance (reviewer fills):** `source` (`drik` | `mpanchang`), `source_url`, `checked_by`,
`checked_on`

Times: local clock times as the reference presents them for `sunrise`/`sunset`/`rahu_kaal_*`;
**UTC ISO-8601** for the `*_end_utc` boundary instants, since a boundary near local midnight is
ambiguous in local time and that ambiguity is exactly what S1 tests.
